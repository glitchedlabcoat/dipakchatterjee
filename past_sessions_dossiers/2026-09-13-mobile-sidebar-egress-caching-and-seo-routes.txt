[889408d — 14:13:54] Egress-reduction data-layer caching on public pages
  Event/Issue: task asked for `export const revalidate = 60` on public
  pages for page-level ISR. `next build`'s route table showed the homepage
  stayed `f (Dynamic)`, never became static — the export was a silent no-op.
  Root Cause: proxy.ts's per-request CSP nonce (`script-src 'nonce-...'
  'strict-dynamic'`) requires dynamic rendering site-wide per Next's own
  docs, and every route was already forced dynamic via `cookies()` inside
  the cookie-reading Supabase client. THIS IS THE ORIGIN OF THE STANDING
  "CSP NONCE BLOCKS ISR" PROJECT-MEMORY RULE.
  Decision point: posed an explicit choice — (A) cache at the data layer,
  keep strict CSP, vs. (B) relax CSP to enable real page-level ISR. User
  chose (A).
  Resolution: new cookie-free `utils/supabase/public.ts` (`createPublicClient()`
  wrapping `@supabase/supabase-js` directly — safe to call inside
  `unstable_cache`, unlike the cookie-reading `@supabase/ssr` client, which
  trips a Dynamic API and breaks caching); new `lib/cache.ts`
  (`PUBLIC_CACHE_TAG = "public-content"`, `revalidatePublicPages()` calling
  `revalidateTag(tag, {expire: 0})` — `{expire: 0}` chosen over Next 16's
  `"max"` profile specifically because `"max"` serves stale content during
  background revalidation, contradicting "an admin's save must be reflected
  on the very next public page load"). Wrapped Supabase reads across
  app/(site) in `unstable_cache(fn, keyParts, {revalidate: 60, tags:
  [PUBLIC_CACHE_TAG]})`; wired `revalidatePublicPages()` into ~20 admin
  mutation call sites that previously called `revalidatePath("/")`.
  Critical bug caught before shipping: after switching app/(site)/page.tsx
  off the cookie-reading client, `next build` showed `/` flip to fully
  Static (`Revalidate: 1m, Expire: 1y`) — an unintended side effect, since
  no other Dynamic API remained in that route's render path. Verified via
  `npm run start` + curl (twice), diffing the CSP response header's nonce
  against the nonce embedded in the cached response HTML's `<script>` tags —
  they diverged after the first request, which would make a real browser
  block every nonced script as a CSP violation (broken hydration). Fixed by
  adding `export const dynamic = "force-dynamic"` to app/(site)/page.tsx.
  Verified caching itself still worked: a temporary console.log inside the
  data-fetch function showed 5 requests → 1 actual DB execution.
  Also bumped Supabase Storage upload `cacheControl` from 1 hour to 30 days
  across every upload site; added `images.minimumCacheTTL: 86400` to
  next.config.ts (noted as currently inert since the app renders all media
  via plain `<img>`, never `next/image`).

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE
--------------------------------------------------------------------------------
- Cache at the Supabase data-fetch layer (unstable_cache + cookie-free
  client), not at the Next.js route/page level: proxy.ts's per-request CSP
  nonce makes page-level ISR structurally impossible site-wide. Relaxing
  the CSP to allow real ISR was explicitly offered and explicitly REJECTED
  by the user. This is the single most-referenced architectural constraint
  in this project's history from this day forward.
- `revalidateTag(tag, {expire: 0})` over `"max"`: `"max"` serves stale
  content while revalidating in the background, contradicting "an admin's
  save must be reflected on the very next public load."
- `export const dynamic = "force-dynamic"` placed on the LAYOUT, not just
  the page: the layout's data fetch runs for every page under that route
  group, so forcing dynamic only on the homepage left every other (site)
  page still vulnerable to the same build-time-probe failure mode.
- `createTrackedCache`'s hit/miss detection uses a monotonic per-route
  counter stamped into the cached value, chosen specifically because it is
  provably race-safe under Next's documented request-coalescing behavior
  for same-key concurrent cache misses, with no assumptions about internal
  scheduling.
- ONE shared `0..n-1` reorder index written across BOTH `features.
  display_order` and `phases.sort_order`, not a new polymorphic "sections"
  table: works because sorting each table independently and merging by raw
  numeric value exactly reconstructs interleaved order, provided both are
  always written from the same shared sequence — chosen over a materially
  larger schema migration for zero functional gain given neither table
  holds more than a handful of rows.
- Global `gallery_interval_ms` → per-item `slideshow_interval`: the new
  requirement is inherently per-row; the superseded global column was left
  in place, unused, rather than dropped, matching this project's established
  precedent for retired settings columns.
- `MobileSidebarContext` via React Context, not lifted `useState`/prop-
  drilling or a global event bus: the hamburger trigger and the drawer
  itself are not adjacent in the JSX tree, and their nearest common ancestor
  is the async Server Component layout, which cannot hold `useState`.
- Changelog format: entries from v1.9.0 onward use Keep-a-Changelog
  subheadings; earlier entries keep their original "Summary of What
  Changed"/"Files Edited" format rather than being retroactively rewritten
  — an explicit, deliberate convention stated in both files' own header.
