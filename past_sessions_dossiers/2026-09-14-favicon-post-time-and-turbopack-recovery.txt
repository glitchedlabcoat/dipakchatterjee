  (3.1) Sticky admin sidebar — regression fix
  Event/Issue: on long admin pages, the sidebar's bottom cluster (View Live
  Site / user label / Sign out) scrolled away with the page content.
  Root Cause: the layout's outer wrapper was an unbounded, growable
  `<div className="min-h-screen flex">`; `AdminSidebar`'s `<aside>` used
  `md:static` at the desktop breakpoint, which OVERRIDES `fixed`, dropping
  the sidebar into normal document flow (mobile stayed correctly fixed —
  the bug was desktop-only).
  Resolution: outer wrapper changed to `h-screen flex overflow-hidden` (so
  the page itself never scrolls); `<main>`'s inner content wrapper became
  the actual scrolling pane; the sidebar filled its now-fixed-height parent
  via `h-full` instead of needing `fixed`/`sticky`; the sidebar's own middle
  nav-links list got `flex-1 min-h-0 overflow-y-auto` so ONLY that list
  scrolls internally if it overflows, while the top brand block and bottom
  user/sign-out cluster got `shrink-0` so they can never be compressed away.

  (3.2) "Include Time" not reflecting on public pages — regression fix
  Event/Issue: checkbox checked, real timestamp present in the admin, but
  public pages still showed date only.
  Root Cause (found via a direct live-database REST query, not code
  inspection alone): `curl .../posts?select=...,show_published_time` →
  `{"code":"42703",...,"message":"column posts.show_published_time does not
  exist"}`. The same for `site_title`. Confirmed via `supabase migration
  list`: both of Phase 2's migrations showed `"remote":""` — written to
  disk but NEVER APPLIED to the live project. The code itself (formatPostDate,
  the checkbox wiring, the conditional-spread logic) was independently
  confirmed correct — this was purely an unapplied-migration bug.

  (3.3) Navbar avatar showing "DC" instead of the real photo — a REAL
        regression this time
  Root Cause: live-queried and confirmed a real, valid, 200-resolving
  `avatar_url` now existed — the image asset itself was fine. Traced instead
  to `getSiteChrome()`'s query, which selected `site_settings` using an
  EXPLICIT NAMED COLUMN LIST that included `site_title` — a column
  confirmed (3.2) not to exist live. PostgREST rejects a SELECT's ENTIRE

  symptom: Next's on-disk Data Cache (`.next/cache`) had persisted the
  stale/errored cached result from before the fix and survived a plain
  process restart. Fix: `rm -rf .next` + restart.

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE
--------------------------------------------------------------------------------
- Title-template ownership installed at `app/(site)/layout.tsx`, not the
  true root: a documented, explicitly-flagged deviation from the literal
  prompt, avoiding a large, unrequested, cross-cutting title-doubling
  breakage across every admin page.
- React `cache()` wrapping around `generateMetadata`'s data source:
  `generateMetadata` and the page/layout component are both invoked once
  per request for the same data — without `cache()`, both call sites would
  independently query the Data Cache, doubling cache-telemetry counts
  without any real additional Supabase egress.
- `select("*")` over an explicit named-column list for `site_settings`:
  PostgREST rejects a query's entire result if even one named column
  doesn't exist yet — turning a single not-yet-migrated column into a
  site-wide chrome outage. `select("*")` degrades gracefully instead, and
  this fix specifically EXTENDS an already-proven convention used elsewhere
  in the same file (the `nav_links` query), rather than inventing a new one.
- `h-dvh`-class sticky-layout technique (the sidebar-scroll fix) was later
  discovered, the very next day, to have a mobile-specific edge case of its
  own — see the 2026-09-13 dossier's own sidebar work and later sessions'
  `h-dvh` refinement for the full resolution; this day's fix used
  `h-screen`, corrected to `h-dvh` in a subsequent session once a mobile
  Safari/Chrome toolbar-clipping issue was found.
- Diagnostic-script discipline maintained: temporary favicon-generation
  scripts written, run, and deleted within the same turn, never committed.
- Turbopack cache corruption attributed to repeated force-kills, not fixed
  by "avoid force-killing" as a rule going forward — the practical fix
  (clear `.next/cache` on any future unexplained Turbopack panic) is the
  durable, actionable lesson, since some force-kills are unavoidable when a
  dev server must be stopped quickly.
