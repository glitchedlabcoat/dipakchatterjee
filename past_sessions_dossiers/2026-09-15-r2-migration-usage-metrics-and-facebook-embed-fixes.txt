[Sequence Step 1 — 2026-09-15, prior to 15:26:24 +0530]
  * Event / Issue: `scripts/migrate-supabase-to-r2.ts` threw an R2
    authorization header error when run against `.env.local`.
  * Root Cause: Values read from `.env.local` (e.g. R2 credentials) retained
    trailing/embedded CR (`\r`) characters and/or surrounding quote
    characters when the file was parsed line-by-line, corrupting the
    Authorization/Signature headers sent to R2's S3-compatible API — a
    classic CRLF-vs-LF line-ending artifact.
  * Resolution: Added a `sanitize()` helper stripping surrounding quotes and
    any `\r`/`\n` characters from every parsed `.env.local` value before use:
      ```ts
      const sanitize = (val?: string) => val?.trim().replace(/^["']|["']$/g, "").replace(/[\r\n]/g, "") || "";
      const env = Object.fromEntries(
        fs.readFileSync(envPath, "utf8").split("\n").filter(Boolean).map((line) => {
          const i = line.indexOf("=");
          return [line.slice(0, i), sanitize(line.slice(i + 1))];
        })
      ) as Record<string, string>;
      ```
    Script was then run for real against production data.
  * Result: 402 files transferred, 0 failed, 390 Supabase DB rows updated to
    point at their new R2 keys/URLs.

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE
--------------------------------------------------------------------------------
- **Separate private R2 bucket for complaint media, no public domain ever
  attached**: The existing admin-media R2 bucket has a bucket-wide
  public-access toggle used for portfolio images. Citizen complaint
  submissions are sensitive (potentially containing identifying photos/
  location data tied to a real complaint). Putting them in the same bucket
  would mean a single future toggle flip could expose all citizen media.
  Physically separate buckets make that class of mistake structurally
  impossible rather than relying on per-object ACL discipline.
- **Presigned direct-to-R2 upload instead of server-proxied upload**: Avoids
  routing potentially large video payloads through the Next.js server
  (memory/timeout risk on serverless-style hosting), and keeps the server's
  role limited to authorization + validation (rate limit, content-type
  allowlist, size caps, `draftId` UUID check) rather than data transfer.
- **WebCodecs re-encode only as a fallback, not the default path**: Fast-
  tracking any video ≤10 MB with no re-encoding minimizes both client CPU
  cost and upload latency for the common case; the WebCodecs `VideoEncoder`
  + `mp4-muxer` re-encode (720p/30fps/1.2Mbps) is reserved for the minority
  of oversized clips, trading a heavier client-side operation for still
  avoiding any server-side transcoding infrastructure (no ffmpeg service to
  host/pay for). The 1.2 Mbps target at 720p/30fps was chosen as a
  reasonable quality/size tradeoff to land clips under the 10 MB fast-track
  ceiling within the 60-second duration cap (≈1.2 Mbps × 60s ≈ 9 MB video
  track, leaving headroom for audio + container overhead under 10 MB).
- **`unstable_cache` (3600s) for R2 usage stats rather than live per-request
  fetch**: Matches an existing session rule (see
  [[project_csp_nonce_blocks_isr]] in persistent memory) that `proxy.ts`'s
  per-request CSP nonce forces dynamic rendering site-wide, so page-level
  `revalidate` is a no-op anywhere in this app — caching for expensive
  aggregate operations (like listing/summing R2 objects) has to happen at
  the data-fetch layer via `unstable_cache`, not via route-segment caching.
- **Cloudflare Analytics ("Advanced" usage tier) fully optional and
  degrade-to-null**: `CLOUDFLARE_API_TOKEN` was never verified against a
  live Cloudflare account in this session (explicitly caveated in code
  comments), so the entire Advanced-tier data path was built to fail soft —
  any GraphQL/auth error returns `null` and the UI simply omits that
  section, rather than the whole Usage Metrics page erroring out for admins
  without the token configured.
- **XFBML Social Plugin over Graph API oEmbed for Facebook embeds**: The
  Graph API oEmbed endpoint (`plugins/post.php` driven by an App ID/Secret
  through the Graph API) requires Meta Business Verification (tied to
  GSTIN/business registration) to work reliably in production; this app
  does not have that verification. XFBML is Meta's own documented
  alternative that renders via a client-side SDK script and never calls the
  Graph API at all, sidestepping that gate entirely — at the cost of
  needing to be a `"use client"` component with its own SDK-lifecycle
  management (fb-root singleton, re-parse-on-navigation) rather than a
  simple server-rendered iframe.
- **Kept the Meta App ID/Secret Settings fields in place despite not being
  used by the new XFBML path**: Explicit user requirement — those fields
  remain for potential future use once/if Business Verification is
  obtained, at which point the Graph API oEmbed path could be re-enabled
  without rebuilding settings UI.
- **fb-post vs. fb-video as two genuinely separate plugins, not a single
  smart plugin**: This is a hard constraint of Meta's own XFBML
  implementation (confirmed via Meta's integration docs, referenced in
  code comments) — not a design choice available to this codebase. The fix
  had to branch on content type because Meta's plugin itself has no
  auto-detection.
  Formats/orientation:
    - `vertical` → 9:16 portrait frame (Reels/Shorts).
    - `horizontal` → 16:9 locked frame (regular video).
    - `auto` → natural height, used for plain photo/text posts whose shape
      isn't reliably one ratio or the other.
- **MutationObserver + timeout, not a single mechanism alone, for XFBML
  mount-failure detection**: A pure timeout risks false-positive fallback
  firing on a slow-but-legitimate SDK load; a pure MutationObserver with no
  timeout risks hanging forever if the SDK never loads at all (ad blocker,
  network failure). Combining both (observer resolves early on success,
  8-second timeout as a hard backstop) gives fast success-path detection
  without an unbounded failure-path wait.
- **Iframe `onError` fallback chain limitation, explicitly documented rather
  than silently accepted**: Cross-origin iframes give the embedding page no
  API to detect "the iframe loaded successfully (HTTP 200) but its own
  content is an error/unavailable message" — this is a genuine, permanent
  browser platform limitation, not something more client code could fix.
  The code comments in both `PostEmbed.tsx` and `FacebookEmbed.tsx`
  explicitly document this boundary so a future maintainer doesn't waste
  time trying to "fix" an unfixable class of failure.
- **Real-browser (Playwright + system-installed Edge) verification chosen
  over curl for the Facebook diagnostic**: `curl` was proven unreliable for
  this specific verification because Facebook's own bot-detection blocks
  the request pattern itself (returning HTTP 400 regardless of content
  validity, confirmed via a control test against a known-working post's
  plain permalink). A real browser with a real session/TLS fingerprint was
  required to get a signal that actually reflected user-visible behavior.
  `playwright-core` (not full `playwright`, to avoid downloading a bundled
  Chromium) was pointed at the already-installed system Edge binary rather
  than installing a new browser, since no other automation tooling was
  available in the environment and installing a new browser binary was
  avoidable overhead.
- **Diagnostic scripts kept out of the repository**: `check-fb-embed.mjs`
  and `check-fb-embed2.tmp.mjs` were one-off verification tools, not
  application code — created in the scratchpad directory (and briefly the
  project root, to resolve Node module path issues) and deleted immediately
  after use, never staged or committed.
- **Changelog: preserve historical entries' original format, only apply Keep
  a Changelog subheadings going forward**: Explicit user instruction to
  preserve existing valid entries and avoid churn/reformatting risk on
  content that was already correct; new-format entries were additive only.
- **Changelog entries never self-reference their own introducing commit's
  hash** (memory rule [[feedback_changelog_commit_hash]]): citing a commit's
  own hash inside that same commit's changelog entry is self-invalidating,
  since the act of adding the reference would itself need to be part of
  that same commit, and any later amendment changes the hash again. Entries
  either omit the hash or reference a prior, already-fixed commit.
