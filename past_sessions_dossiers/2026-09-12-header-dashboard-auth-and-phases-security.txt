[9c8e6fc — 16:42:50] Server Action redirect race on login; profile upsert;
broken new-user trigger
  Bug 1 — "Failed to fetch" on /admin/login despite the user actually being
  signed in:
  Root Cause: `signInWithPassword()` sets the session cookie synchronously
  before the next line calls the `requestLoginOtp()` Server Action, which
  Next implements as a fetch POST back to the SAME URL (/admin/login).
  proxy.ts runs on every matching request including that POST; with
  REQUIRE_OTP off, `isOtpVerified = Boolean(user)` is now true for that very
  POST (the cookie was already set), so proxy.ts substitutes a raw HTTP
  redirect AS THE RESPONSE to the Server Action's own fetch — corrupting
  Next's action-response protocol, surfacing as "Failed to fetch" client-side.
  Fix: `const isServerAction = request.headers.has("next-action")` — every
  existing redirect branch in the `/admin` block is now skipped entirely for
  any request carrying that header (generalized to the structurally correct
  invariant, not patched narrowly for the one reported route). Verified by
  deliberately `git stash`-restoring the pre-fix code, reproducing the bug
  on demand (307 redirect on a next-action POST), then restoring the fix and
  reconfirming (404/no-redirect, correctly passed through to Next's action
  dispatcher).
  Bug 2 — `duplicate key value violates unique constraint "profiles_pkey"`
  on new-user creation:
  Root Cause: a pre-existing `handle_new_user()` Postgres trigger already
  auto-inserts a bare profiles row the instant `auth.admin.createUser()`
  succeeds; `createUserAccount`'s own subsequent plain `.insert()` with the
  same id always collided.
  Fix: `.upsert({...}, {onConflict: "id"})` — deliberately omits `role` from
  the payload (it's a Postgres STORED GENERATED column; any write to it is
  always rejected regardless of value) and substitutes `is_admin: false`.
  Bug 3 (deeper, found via a user-pasted log after Bug 2's fix) —
  `auth.admin.createUser()` itself failing with "Database error creating
  new user" (GoTrue wrapper, status 500), for every email, reproducibly:
  Investigation was genuinely blocked for a time — GoTrue hides the real
  Postgres error, and the Supabase CLI had no authenticated project access

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE
--------------------------------------------------------------------------------
- RLS recursion can never be fixed by rewriting a table's own self-
  referential policy — the only way to break the cycle is to source the
  admin-check truth from somewhere RLS evaluation on `profiles` doesn't
  touch (JWT claim, or a SECURITY DEFINER read of a policy-free table).
  `SET search_path = public, pg_temp` on every such function is a
  deliberate, repeated mitigation against search-path-hijack privilege
  escalation, not boilerplate.
- Feature-flag placement (`FEATURE_FLAGS.REQUIRE_OTP`) gates only the two
  call sites that decide whether to invoke the OTP challenge, never deletes
  or comments out OTP code — the requirement was "preserved behind a
  toggle," and a minimal-surface-area boolean short-circuit around
  pre-existing, already-tested logic is lower-risk than any structural
  removal, and trivially reversible.
- `useSyncExternalStore` over `useState`+`useEffect` for hydration/media-
  query detection: collapses a two-render sequence into React's own
  hydration reconciliation, eliminating both the extra render and the
  underlying lint violation — judged a genuine improvement, not lint
  appeasement.
- `eslint-disable` comments (not behavior changes) for `window.location.
  assign` calls: these hard navigations exist specifically to force a fresh
  server-side cookie read with zero client router cache involved — replacing
  them with `router.push()` would reintroduce a previously-fixed bug class.
- Upsert with `onConflict: "id"`, omitting `role`, for `createUserAccount`:
  the only reliable fix given a pre-existing trigger auto-creates the row;
  `role` is a generated column and any write to it fails unconditionally.
- Minimal trigger replacement (not a "smarter" one) for `handle_new_user()`:
  intentionally omits `is_admin` (relies on its column default `false`,
  avoiding any risk of colliding with the deferred single-admin constraint)
  and `full_name` (left to app code, avoiding duplicated business logic
  living in both app code and a hand-maintained SQL trigger — exactly how
  the broken version had drifted in the first place).
  `isServerAction` header check generalized to skip ALL redirect branches
  uniformly, not just the one that produced the observed bug: substituting a
  raw redirect for any Server Action's own request is unconditionally wrong,
  regardless of which branch triggers it.
- Diagnostic-script discipline (consistent across every live-database test
  this day): written into scripts/ (never scratchpad-only, for node_modules
  resolution), throwaway timestamp-suffixed accounts, cleanup always in a
  `finally` block, real production rows independently re-queried before/
  after to positively confirm zero collateral impact.
