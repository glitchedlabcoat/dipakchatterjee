--- MISSION 1: Render OOM re-investigation ------------------------------------

[Step 1.1 — Investigation]
  * User's framing: aggressive in-memory caching (relied on to keep
    egress low) was suspected of accumulating and causing the exit-134
    crash to recur; "clearing cache temporarily resolves it" was offered
    as supporting evidence.
  * Three parallel read-only Explore passes covered: every module-level
    in-memory cache/Map/LRU in the repo, every `unstable_cache` call site
    and its payload size/boundedness, and any on-disk caching precedent;
    a security baseline re-audit of every `app/api/*/route.ts` and server
    action, `NEXT_PUBLIC_*` usage, and `proxy.ts`'s CSP; and the admin
    dashboard/changelog data structure needed for Mission 2.
  * Findings: NO unbounded cache exists anywhere. `lib/rate-limit.ts`'s
    `Map` is capped at 5000 keys (FIFO eviction, unchanged since
    2026-09-16). Every `unstable_cache` call site (6 total, across
    `lib/queries/{posts,settings}.ts`, `app/(site)/layout.tsx`,
    `app/(site)/page.tsx`, `app/(site)/phases/[id]/page.tsx`,
    `lib/r2-usage.ts`) caches only small Postgres row/aggregate data —
    never image/video bytes — behind Next's own built-in Data Cache,
    which is already a size-bounded in-memory LRU defaulting to 50MB
    (`cacheMaxMemorySize`, confirmed via
    `node_modules/next/dist/docs/.../cacheMaxMemorySize.md`), not
    previously overridden in `next.config.ts`. No on-disk cache precedent
    exists anywhere in server runtime code. Security re-audit found ZERO
    regressions from the 2026-09-15/09-16 baselines.
  * Reconciling the user's "clearing cache fixed it" observation: the
    most plausible explanation, given the evidence, is that a Render
    restart (which resets V8's heap usage to baseline) was what actually
    resolved it, not the cache clear itself — consistent with the
    2026-09-16 session's own finding that heap usage plateaus (~250MB
    against a ~256MB auto-sized ceiling) rather than growing unbounded.
  * User, presented with this evidence via AskUserQuestion, instructed:
    assume `NODE_OPTIONS=--max-old-space-size=400` was already added on
    Render's dashboard (the 2026-09-16 session's documented, unverifiable
    action item), still hardware-harden the bounded-cache story in code,
    and report the exact Render env var name/value at the end regardless.

[Step 1.2 — Fix]
  * `next.config.ts`: added an explicit `cacheMaxMemorySize: 20 * 1024 *
    1024` (20MB, down from Next's implicit 50MB default) for the Data
    Cache — makes the existing bound intentional/tighter rather than
    relying on an undocumented default, on a container with little
    headroom to spare.
  * `app/(site)/page.tsx`: `getHomepageSections()`'s four Supabase
    queries (`features`, `phases`, `organizations`, `cta_buttons`) had no
    `.limit()` at all, unlike the admin `posts`/`features` list pages
    (which got `.limit(200)` in the 2026-09-16 session). Added the same
    `.limit(200)` safety-cap pattern here.
  * Considered and explicitly REJECTED: baking `--max-old-space-size=400`
    into `package.json`'s `start` script pointed at
    `.next/standalone/server.js` directly. Reason: this repo's
    `output: "standalone"` build does NOT copy `public/`/`.next/static`
    into the standalone folder by default (confirmed via
    `node_modules/next/dist/docs/.../output.md` — that requires a manual
    `cp -r public .next/standalone/ && cp -r .next/static
    .next/standalone/.next/` step this repo has no evidence of running).
    Whether Render's actual configured Start Command is `npm start` or a
    direct `node .next/standalone/server.js` invocation is unknown from
    inside this repo; changing `package.json`'s `start` script blindly
    risked either doing nothing (if Render bypasses npm scripts) or
    breaking `npm start` locally/on Render (missing static assets if the
    copy step isn't part of Render's Build Command). Since
    `NODE_OPTIONS` as a Render dashboard Environment Variable is already
    invocation-agnostic — Node reads it from the OS environment before
    executing any script, regardless of how the process was started —
    it's the strictly safer, equally effective mechanism, so no
    `package.json`/entrypoint change was made. This was caught and
    reverted mid-session after briefly making the edit.
  * No change to `lib/rate-limit.ts` (already correctly bounded) and no
    new disk-offload/bespoke LRU module built — no evidence exists of a
    payload large enough to justify that complexity, and building it
    would have been speculative scope beyond what the investigation
    found.
  * Reported to the user at session end (per their explicit request):
    Render Environment Variable name `NODE_OPTIONS`, value
    `--max-old-space-size=400`.

--- MISSION B: RangeError root-cause fix + Meta oEmbed UI removal --------------
(separate user-initiated mission, later the same day; committed as e1c6f54)

[Step B.1 — Investigation]
  * A subagent traced every `.toISOString()`/`.toLocaleString()`/
    `Intl.DateTimeFormat` call site in the repo. Root cause of the
    intermittent `RangeError: Invalid time value` in Render logs:
    `app/admin/(protected)/posts/actions.ts`'s `createPost`/`updatePost`
    only truthy-checked the admin's `published_at` form input before
    calling `new Date(input.published_at).toISOString()` — never
    validated it actually parsed. A malformed value (devtools-edited
    field, extension interference) threw uncaught.
  * Every other call site audited was safe: fed either a bare
    `new Date()` (always valid) or a Supabase column enforced `NOT NULL`
    at the schema level.

[Step B.2 — Fix]
  * New `lib/safe-date.ts`: `safeDate`, `safeToISOString`, and
    `parseValidDate` (the one actually used) — each checks
    `Number.isNaN(d.getTime())` before trusting a parsed `Date`.
  * `posts/actions.ts`: added `toValidPublishedAt()` wrapping
    `parseValidDate`; both `createPost`/`updatePost` now use it instead
    of the unguarded inline `new Date(...).toISOString()`.
  * `PostForm.tsx`: added a matching client-side Zod `.refine()`
    (`isEmptyOrParseableDate`) so a bad date is caught as a normal form
    validation error before it ever reaches the server action.
  * Two additional low-risk hygiene fixes applied opportunistically:
    `ChangelogBrowser.tsx`'s `formatDate()` gained a
    `Number.isNaN(date.getTime())` guard (falls back to the raw string
    instead of throwing on a hypothetical malformed changelog date); and
    `/admin/usage`'s `istDateString()` was rewritten to build the IST
    calendar date directly via `Intl.DateTimeFormat("en-CA", {timeZone:
    "Asia/Kolkata"})` + `Date.UTC(...)`, instead of the previous approach
    of round-tripping through `new Date(now.toLocaleString("en-US",
    {timeZone: "Asia/Kolkata"}))` (which re-parses a locale-formatted
    string — fragile, though not proven to have ever actually failed).

[Step B.3 — Removed non-functional Meta App ID/Secret UI]
  * Context: `integration_settings`' schema migration was never actually

--- MISSION D: Render build-time heap OOM fix ----------------------------------
(triggered by a pasted Render deploy-failure log; committed as e535a40)

[Step D.1 — Diagnosis]
  * User pasted a Render build log showing a V8 heap OOM crash during
    `next build`'s TypeScript-check phase (`Mark-Compact (reduce) 399.0
    (404.1) -> 397.3 (400.6) MB ... FATAL ERROR: Ineffective mark-compacts
    near heap limit`) — a NEW failure mode, distinct from the
    already-fixed runtime exit-134 crash (Mission A / the 2026-09-16
    session).
  * Root cause: `NODE_OPTIONS=--max-old-space-size=400` — the Render
    dashboard Environment Variable added specifically to fix the
    *runtime* OOM — applies to every Node process spawned in that Render
    environment, including the build step's own `next build` invocation,
    which never needed that low a ceiling and was being starved of
    headroom during typecheck.
  * Reproduced locally and bit-for-bit confirmed: `NODE_OPTIONS=--max-
    old-space-size=400 npx next build` crashed with the identical
    Mark-Compact/heap-limit signature.
  * This build log also incidentally CONFIRMED, for the first time with
    direct evidence, that `NODE_OPTIONS=--max-old-space-size=400` really
    is set on Render's dashboard (previously only ever an instruction
    given to the user, never independently verifiable from inside this
    repo) — the crash literally could not happen otherwise. It also
    revealed Render's actual configured Build Command for the first
    time: `npm install --include=dev && npm run build && cp -r
    .next/static .next/standalone/.next/static` — confirming the
    standalone-deploy-with-custom-Start/Build-Command scenario Mission
    A's Step 1.2 had explicitly flagged as an unknown risk, and also
    revealing this command never copies `public/` into
    `.next/standalone/` (flagged as a new, still-open action item — see
    Section 6).

[Step D.2 — Fix]
  * `package.json`: `"build"` changed from `"next build"` to `"cross-env
    NODE_OPTIONS= next build"` — clears the inherited env var for just
    this one script's process tree, leaving the runtime `NODE_OPTIONS`
    (via `"start": "next start"`, unchanged) fully intact.
  * Chose `cross-env` (added as a new devDependency,
    `npm install --save-dev cross-env`) over the equivalent bare-shell
    prefix `NODE_OPTIONS= next build` specifically because the bare
    syntax is POSIX-only and fails on Windows `cmd.exe` — this
    developer's local environment (per `AGENTS.md`'s Windows-Bash-vs-
    PowerShell distinction and this session's own tool environment).
  * Re-verified the fix survives the identical forced 400MB ceiling
    (`cross-env NODE_OPTIONS=--max-old-space-size=400 next build`
    succeeds where the unguarded script crashed).

  cache-leak theory the investigation actively disproved, the findings

  server-memory cost Mission 1 was hardening against, for a page that
  doesn't need it.
- `useTransition` on every changelog browser state update, even though
  the underlying data is already fully client-side: the user explicitly
  asked for smooth, non-blocking Date/Version/Mode switching; wrapping in

  the UI responsive if the version history grows substantially longer.
- Full human-readable date formatting via `Intl.DateTimeFormat` parsed
  from a manually-split `YYYY-MM-DD` (not `new Date(dateStr)` directly):
  avoids the classic UTC-midnight-parses-as-previous-day bug in negative-
  UTC-offset timezones, raised as an explicit requirement during plan
  review.

  instruction was to assume it was already set; Mission D's build-log

  Mission D's pasted log: `npm install --include=dev && npm run build &&
  cp -r .next/static .next/standalone/.next/static`. This command never
  copies `public/` into `.next/standalone/` — flagged as a still-OPEN
  action item in Section 6 below; requires a manual Render dashboard
  edit (no dashboard access from this environment).
- GitHub Actions: `DISCORD_WEBHOOK` repository secret. Mission E's own
  diagnosis (immediately above, in the original version of this section)
  — that the intermittent curl-exit-22 failures were Discord-side rate
  limiting — was WRONG, and was corrected the same day in a follow-up
  troubleshooting round (after Mission E's push, not its own numbered
  mission): the user reported the failures were still happening and
  getting frustrating, replaced the Discord webhook with a freshly
  generated one, and the SAME exit-22 failure still occurred on the new
  URL. Testing the new webhook directly with `curl` (outside CI, a plain
  POST to the raw URL) returned HTTP 204 — proof the webhook itself was
  always fine. The real, now-confirmed root cause: Discord hard-rejects
  any embed field value over 1024 characters (a 400, surfaced by
  `curl -f` as exit 22); `.github/workflows/discord-notify.yml`'s
  "Full message" field sent the ENTIRE commit message with no
  truncation, and this repo's own conventional-commit bodies (this
  session's own commits included — several ran 1000+ characters) routinely
  exceed that. The old, now-deleted `scripts/notify-discord.js` had a
  `truncate()` helper for exactly this reason; the GitHub Actions
  workflow never did. Fixed by truncating the "Full message" field to
  1024 chars (1023 + an ellipsis) via a `jq` conditional, verified
  against a 1200-char synthetic test string before shipping, then
  confirmed end-to-end on a real push (run succeeded, message arrived in
  Discord). The `--retry --retry-all-errors` flags from Mission E are
  still worth keeping (genuine transient-error protection) but were
  never what was actually wrong here — don't let a future session
  re-diagnose this as "just retry harder" again.
- `.env.example`'s `DISCORD_WEBHOOK_URL` (a local-only variable, distinct
  from the CI secret above) was removed this session (Mission E) along
  with the local script that read it — Discord notifications are now
  strictly CI-only by design, not just by convention.
- No Supabase database migrations this session. `integration_settings`
  table schema (uuid/text id-column mismatch) explicitly left untouched
