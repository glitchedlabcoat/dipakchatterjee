--- MISSION 1: Render exit-134 (SIGABRT) crash ---------------------------------

[Step 1.1 — Diagnosis]
  * Event/Issue: Render production was crashing repeatedly with exit status
    134. Initial code-level investigation ruled out native-module ABI
    mismatches (no `sharp`/`canvas`/`prisma` actually used at runtime —
    `sharp` only appears as an unused optional peer of Next.js, since the
    app never touches `next/image`, rendering all media as plain `<img>`/
    `<video>` tags) and ruled out the one in-memory Map (`lib/rate-limit.ts`)
    as a leak source (already bounded to 5000 tracked keys with LRU-style
    eviction).
  * User supplied the actual Render log tail on request. Every crash showed
    the identical, unambiguous signature:
      "FATAL ERROR: Ineffective mark-compacts near heap limit Allocation
      failed - JavaScript heap out of memory"
    — a genuine V8 heap-OOM abort, not an assertion failure or native
    crash. Heap usage was consistently ~250MB against a V8-auto-sized
    ~256-257MB ceiling on every single occurrence, with NO growth trend
    across restarts (ruling out a classic unbounded leak — this was a
    working-set-vs-ceiling mismatch, not a leak).
  * Root Cause: two compounding factors. (a) V8 auto-sized its old-space
    heap ceiling to ~256MB on this 512MB Render container, leaving almost
    zero headroom over the app's own normal SSR steady-state footprint.
    (b) `app/api/admin/upload/route.ts` fully buffered every uploaded file
    in memory (`request.formData()` + `Buffer.from(await
    file.arrayBuffer())`, effectively ~2x the file size in transient RSS)
    with `MAX_VIDEO_BYTES` set to 100MB — a single admin video upload could
    transiently double-buffer ~200MB directly on top of the ~250MB
    baseline, explaining crashes that didn't correlate with public traffic
    volume (the site owner logging in to upload media).
  * Secondary log findings, NOT the OOM cause, left unfixed and flagged:
    a recurring `RangeError: Invalid time value at Date1.toISOString`
    (non-fatal, has a Next.js error digest; root cause not identified —
    ruled out `lib/post-date.ts`'s `formatPostDate` (uses `toLocaleString`,
    not `toISOString`) and `app/sitemap.ts` (only ever uses `new Date()`,
    never a stored value)), and the already-known, already-deprioritized
    `integration_settings` id-column uuid/text mismatch from a prior
    session (see 2026-09-15's dossier).

[Step 1.2 — Fix]
  * `app/api/admin/upload/route.ts`: `MAX_VIDEO_BYTES` reduced 100MB → 25MB
    — bounds a single request's worst-case memory spike to something the
    container can safely absorb even without a heap-ceiling change.
  * `next.config.ts`: `experimental.serverActions.bodySizeLimit` reduced
    30mb → 1mb — this had been sized for a complaint-form FormData upload
    path that no longer exists (complaints now upload directly to R2 via
    presigned URLs, per 2026-09-15's R2 migration); every remaining Server
    Action in the app only ever sends small JSON payloads.
  * New `instrumentation.ts` / `instrumentation-node.ts`: periodic
    `process.memoryUsage()` logging (15-minute interval, Node-runtime-only
    via a dynamic `import()` so Turbopack's Edge Runtime bundle never has
    to statically resolve `process.memoryUsage`, which doesn't exist
    there) plus an `onRequestError` hook logging server-side errors with
    their digest — so a future incident leaves a diagnosable trace instead
    of a bare native stack trace.
  * `.env.example`: documented `NODE_OPTIONS=--max-old-space-size=400` as
    the actual heap-ceiling raise, explicitly noting it must be set as a
    Render dashboard Environment variable (Node reads `NODE_OPTIONS` before
    it even parses `.env.local`) — the one action this session could not
    perform itself (no Render dashboard access), left for the account
    owner.
  * Verified: `tsc --noEmit` clean, production build clean, and a local
    standalone-server smoke test (`HOSTNAME=0.0.0.0 NODE_OPTIONS=
    "--max-old-space-size=400" node .next/standalone/server.js`) hitting
    every key route (homepage, /notable-works, /sitemap.xml, /robots.txt,
    /complaints) — all 200.

--- MISSION 2: Admin dashboard latency, rage-click pile-ups, inactivity timer -

[Step 2.1 — Root-cause research]
  * Delegated a read-only research pass covering: navigation mechanism,
    per-page data-fetching cost, heavy client components, and the
    inactivity timer's exact event listeners. Findings:
    - No `useTransition`/pending state anywhere gated actual navigation
      (only local form-save/delete actions already used it); no
      `loading.tsx` and no `<Suspense>` boundary existed anywhere under
      `app/admin`.
    - `proxy.ts` → `updateSession()`, the layout, and (on Overview/
      Settings) the page itself each independently called
      `supabase.auth.getUser()` — up to 3 sequential Supabase Auth round
      trips before any page-specific data fetch even started, on every
      single admin navigation.
    - `/admin/settings` ran an unconditional 9-query `Promise.all` on
      every load regardless of which of 6 tabs was active — `SettingsTabs`
      only ever rendered one tab's data.
    - `/admin/complaints` fanned out a presigned-URL/signed-URL generation
      call per media item per complaint on every load (later determined,
      on inspection, to be mostly free local cryptographic work for R2
      objects — `getSignedUrl` from `@aws-sdk/s3-request-presigner` never
      makes a network call — with only the shrinking legacy Supabase
      Storage branch being real network cost; deprioritized as a lower-
      impact item than initially estimated).
    - `next/dynamic` was used nowhere in the codebase; 10 files
      (including most of `/admin/settings`'s tab managers) imported
      `@dnd-kit` directly at module scope.
    - `posts`/`features`/`phases` admin lists used unbounded
      `select('*')` with no `.limit()`.
    - `SessionTimer.tsx`'s activity-reset listeners were `["pointerdown",
      "keydown", "scroll", "touchstart"]` — including passive `scroll`,
      contrary to the desired behavior.
  * Consulted the current (non-standard, pinned) Next.js docs before
    building anything: confirmed a load-bearing caveat — "If the layout
    accesses uncached or runtime data (cookies(), headers(), or uncached
    fetches), loading.tsx will not show a fallback for it... Navigation
    blocks until the layout finishes rendering" (without Cache Components,
    which this app does not use). Since `app/admin/(protected)/layout.tsx`
    itself does an uncached `auth.getUser()` + profile fetch, a
    `loading.tsx` alone could never mask that first, unavoidable stretch of
    every navigation — this directly motivated Step 2.2's client-side
    pending-state approach as the primary lever, with `loading.tsx` only
    covering what happens after the layout resolves.

[Step 2.2 — Instant navigation feedback + click-guard]
  * New `components/admin/AdminNavPendingContext.tsx`: a `useTransition`-
    backed shared pending state (`isPending`, `navigate(href)` wrapping
    `router.push` in `startTransition`), covering the FULL navigation
    window including the layout's own blocking auth fetch (unlike
    Suspense/loading.tsx, which can't reach that far).
  * New `components/admin/AdminTopProgressBar.tsx`: a dependency-free CSS
    top bar shown while `isPending`.
  * `components/admin/AdminSidebar.tsx`: every nav `<Link>` (top-level nav
    items and Settings sub-tab links) now intercepts a plain left-click
    (explicitly passing through modified clicks — ctrl/cmd/shift/alt/
    middle-click — so "open in new tab" still works natively), routes it
    through the shared `navigate()`, and disables itself
    (`pointer-events-none opacity-50` + `aria-disabled`) while a navigation
    is already in flight — the primary defense against a rage-click
    stacking concurrent requests, with an `isPending`-gated early return
    inside the click handler itself as a second line of defense for
    non-pointer activations (e.g. Enter on a focused link).
  * New `app/admin/(protected)/loading.tsx`: a shared skeleton, enabling
    partial route prefetching for every dynamic admin route and masking
    each destination page's own remaining data-fetch time once the layout
    itself has resolved.

[Step 2.3 — Reduced/deduplicated data fetching]
  * New `lib/admin-auth.ts`: `getAuthedUser()` / `getViewerProfile(id)`,
    both wrapped in React's `cache()` (request-scoped memoization, the
    standard documented App Router pattern — carries no cross-user
    leakage risk since Next resets the cache per request). The admin
    layout, Overview page, and Settings page were all refactored to call
    these instead of independently querying Supabase Auth/Postgres,
    collapsing up to 3 sequential round trips per navigation down to 1.
  * `app/admin/(protected)/settings/page.tsx`: rewritten to fetch
    `site_settings` unconditionally (cheap, single row, needed by nearly
    every tab) and every other table ONLY when `activeTab` actually needs
    it (e.g. `organizations`/`integration_settings` only for the "media"
    tab, `nav_links`/`header_actions` only for "header"), replacing the
    prior unconditional 9-query fetch.
  * `app/admin/(protected)/posts/page.tsx`, `features/page.tsx`: added
    `.limit(200)` to the previously-unbounded list queries — a safety cap
    (not real pagination) chosen specifically because it's essentially
    risk-free at current real row counts while closing the unbounded-
    growth part of the memory-risk concern this shares with Mission 1.

[Step 2.4 — Bundle weight]
  * `app/admin/(protected)/settings/page.tsx`: the 6 heaviest `@dnd-kit`-
    consuming Settings managers (OrganizationsManager, CtaButtonsManager,
    FooterBlocksManager, SocialLinksManager, HeaderNavigationManager,
    UsersManager) converted to `next/dynamic(() => import(...))` (without
    `ssr: false`, since that option is illegal in a Server Component in
    this Next.js version — confirmed via the docs) — since `SettingsTabs`
    only ever renders `panels[active]` into the tree, and Next's bundler
    otherwise has to include every statically-imported Client Component in
    a route's client chunk regardless of runtime rendering choices, this
    means the `/admin/settings` route's client bundle now only pays for
    whichever single tab is actually open.

[Step 2.5 — Inactivity timer refinement]
  * `components/admin/SessionTimer.tsx`: `ACTIVITY_EVENTS` changed from
    `["pointerdown", "keydown", "scroll", "touchstart"]` to
    `["pointerdown", "keydown"]` — `scroll` removed entirely (a session
    left merely scrolled must still expire on schedule, not be kept alive
    indefinitely); `touchstart` dropped as redundant, since the unified
    Pointer Events API already fires `pointerdown` for touch, mouse, and
    pen alike.

[Step 2.6 — Verification]
  * `tsc --noEmit` clean, production build clean (no Turbopack warnings —
    an initial version of `instrumentation.ts` in Mission 1 had triggered
    an Edge Runtime bundling warning for the same reason `next/dynamic`
    needed care in Step 2.4; both resolved via the same
    dynamic-import-to-avoid-static-Edge-bundling technique), and a local
    standalone-server smoke test confirming every admin route correctly
    307-redirects to `/admin/login` when unauthenticated (no crashes, no
    server errors in the log).

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE
--------------------------------------------------------------------------------
- Debouncing/click-guarding implemented via `useTransition` + a shared
  Context, not a simple `disabled` flag on individual buttons: a shared
  `isPending` lets EVERY nav trigger disable itself the instant ANY one is
  clicked (not just the one that was clicked), which is what actually
  prevents a rage-click across different sidebar links from stacking
  multiple concurrent RSC fetches — a per-button-only guard would still
  allow clicking a second, different link while the first navigation is in
  flight.
- `next/dynamic` without `ssr: false` (not a Client Component wrapper) for
  code-splitting the Settings managers: this Next.js version rejects
  `ssr: false` inside a Server Component at build time; the plain
  `dynamic(() => import(...))` form still code-splits (a separate chunk,
  lazily requested only when that element is actually rendered into the
  tree) while remaining legal to call from `settings/page.tsx`, which is
  itself an async Server Component.
- Inactivity-timer event filtering (`pointerdown`/`keydown` only): a
  deliberate, explicit product decision, not just a technical cleanup —
  passive scrolling must not count as "the admin is actively using this
  session," so that a tab left open and merely scrolled through still
  expires on schedule rather than being kept alive indefinitely.
- Dead-code elimination judged complete after a systematic (lint +
  targeted grep) pass rather than pursuing an exhaustive manual line-by-
  line audit indefinitely — this repo's own prior sessions had already
  done comparable passes (see 2026-09-12's ESLint stand-up), and a second
  pass finding genuinely nothing is itself a valid, reportable outcome.
- Dossier consolidation grouped by the CALENDAR DATE the underlying git
  commits actually landed on (not by which chat session produced the
  dossier, and not by a session's own self-reported multi-day date range)
  — since the whole point of this reorganization was to make "what
  happened on day X" answerable by opening exactly one file, and several
  source files' own filenames/date claims did not match their content's
  actual commit dates.
