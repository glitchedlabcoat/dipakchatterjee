[Step 8 — Discord CI notifications: root-cause misdiagnosis, correction,
  and the real fix]
  * Event 8a: user reported ongoing Discord CI failures were
    "pissing me off" and asked for troubleshooting INSTRUCTIONS ONLY, no
    file changes. Given a 5-step manual checklist (verify the webhook
    still exists in Discord, confirm the GitHub secret matches, test the
    raw webhook URL directly outside CI, read the actual failing step's
    raw output, consider Discord rate limits).
  * Event 8b: user pasted a GitHub Actions annotation screenshot showing
    the OLD webhook still failing (`Process completed with exit code
    22`), reported they had just replaced the Discord webhook with a
    freshly generated one, and pasted that new webhook's full URL in
    chat, asking to fix it.
  * Root Cause (first hypothesis, later disproven): the pattern of one
    success + two exit-22 failures on the OLD webhook had earlier been
    diagnosed as Discord-side rate limiting. Updating the GitHub secret
    to the new URL (via `gh secret set DISCORD_WEBHOOK`, piped through

    workflow never did.

    the "Full message" field changed to
    `(if ($message | length) > 1024 then ($message[0:1023] + "…") else

    1200-character string truncated to exactly 1024 chars ending in the
    ellipsis) before committing. Re-ran the workflow on the real push:
    full green run including the Notify Discord step; user confirmed in
    Discord that the message arrived.
  * Associated Commit Hash: 6cf1deb (the truncation fix). The GitHub

[Step 10 — THE REAL RENDER OOM ROOT CAUSE: Supabase client auto-refresh
  ticker leak]
  * Event: user pasted a SECOND, later Render crash log. Its
    instrumentation.ts-sourced periodic memory readings (15-minute
    interval) showed `rss` climbing smoothly and monotonically from
    275.2MB to 482.3MB over roughly 2 hours before the crash
    (`FATAL ERROR: Ineffective mark-compacts near heap limit Allocation
    failed - JavaScript heap out of memory`), then — after Render's
    automatic restart — climbing again from 171.6MB at the SAME rate
    over the next ~2.5 hours (to 372.1MB) before the log was pasted.
  * Root Cause: this shape (smooth, monotonic, resets-and-repeats-
    identically-after-restart) can only be produced by genuine ongoing
    accumulation, not a one-time heap-ceiling/headroom mismatch (which
    would plateau near the ceiling, not keep climbing past it) — directly
    contradicting the "not a leak" conclusion this same session (and the
    2026-09-16 session before it) had drawn from shorter observation
    windows. Investigation traced it to `utils/supabase/public.ts`'s
    `createPublicClient()` and `utils/supabase/admin.ts`'s
    `createServiceClient()`, both of which called plain
    `@supabase/supabase-js` `createClient()` without disabling
    `autoRefreshToken` (public.ts passed no auth options at all;
    admin.ts passed only `persistSession: false`, which does NOT control
    this). Read directly from
    `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js`: its
    `_handleVisibilityChange()` method starts an un-cleared
    `setInterval` token-refresh ticker unconditionally in any
    non-browser environment — its own comment says "in non-browser
    environments the refresh token ticker runs always." The ticker is
    `unref()`'d (doesn't block process exit) but is NEVER cleared, so
    its closure keeps the entire client instance (postgrest/realtime/
    storage sub-clients, in-memory storage, everything) alive in the
    heap permanently. `createPublicClient()` is called fresh (not
    memoized/reused) inside 6 separate `unstable_cache`-wrapped public
    read functions (`getHomepageSections`, `getSiteSettings`,
    `getSiteChrome`, `getPublishedPhase`, `getPostsList`, `getPostById`)
    on every cache miss — so real traffic left a steadily growing
    population of zombie Supabase clients, each pinned in memory by its
    own permanent 30-second ticker
    (`AUTO_REFRESH_TICK_DURATION_MS = 30 * 1000`, confirmed in
    `node_modules/@supabase/auth-js/dist/main/lib/constants.js`).
    Separately confirmed `utils/supabase/server.ts` (the per-request
    cookie-based admin client, via `@supabase/ssr`'s
    `createServerClient`) was NOT affected — that library already
    defaults `autoRefreshToken: false` itself (confirmed by reading
    `node_modules/@supabase/ssr/dist/main/createServerClient.js`),
    unlike plain `@supabase/supabase-js`.
  * Resolution: both `utils/supabase/public.ts`'s `createPublicClient()`
    and `utils/supabase/admin.ts`'s `createServiceClient()` now pass
    `{ auth: { autoRefreshToken: false, persistSession: false,
    detectSessionInUrl: false } }`. Zero behavior change to any actual
    query — neither client ever legitimately has a user session to
    refresh (public.ts is always anonymous; admin.ts is a service-role
    key). Verified directly, not just by reading source: a standalone
    script (`__leak-check3.mjs`, written to the repo root, run, then
    deleted — never committed) monkey-patched `global.setInterval` to
    count calls, then constructed 5 clients the OLD way (5 setInterval
    calls recorded — one permanently leaked ticker per client) followed
    by 5 more the NEW way (0 additional setInterval calls). This is
    conclusive proof, not inference.
    `npm run lint`/`npm run build` both clean afterward.
  * Associated Commit Hash: 293fd7d (the fix).
  * Follow-up: added a new Section 8 ("Critical Correction: The Render
    OOM Was A Real Leak All Along") to the OTHER 2026-09-17 dossier file,
    explicitly marking Section 1's Context and Mission 1/Step 1.1's
    findings in that file as superseded on the "no leak exists" point,
    and recording a standing lesson: a short memory-log observation
    window cannot distinguish "plateaus near a ceiling" from "climbs
    slowly and crashes later," and any future crash recurring AFTER a
    `NODE_OPTIONS` ceiling raise should be treated as evidence FOR a
    leak, not against one.
  * Associated Commit Hash (dossier correction): 31cf058.

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE
--------------------------------------------------------------------------------
- One shared `lib/site-url.ts` constant instead of per-file hardcoded
  origin strings: guarantees `app/layout.tsx`, `app/(site)/layout.tsx`,
  `app/sitemap.ts`, and `app/robots.ts` can never drift out of sync on
  the canonical domain again.
- `metadataBase` stays on the TRUE root `app/layout.tsx` (not the
  `(site)` route group's layout) specifically so it applies to `/admin`
  routes too, per Next's own documented guidance.
- Per-page canonicals implemented as each route's OWN
  `alternates.canonical` rather than a blanket root default: Next's
  metadata merging means an unset child field inherits the parent's, so
  a root-level canonical is only ever correct for the literal homepage
  — anything else silently mis-canonicalizes. This was a real mistake
  made in Step 1 and corrected in Step 4, not a hypothetical risk.
- `cross-env NODE_OPTIONS= next build` over a bare shell-prefix
  (`NODE_OPTIONS= next build`): the bare POSIX syntax silently fails (or
  behaves differently) on Windows `cmd.exe`, this developer's local
  shell — `cross-env` is the only approach that's correct in both
  environments without a platform-conditional script.
- Discord notification architecture: CI-only by design, not just by
  convention — the local `deploy:push`/`notify:discord` path was deleted
  entirely rather than merely discouraged, removing the possibility of a
  local machine independently posting to the same webhook outside of
  CI's own guardrails (including, now, the message-length truncation).
- `--retry --retry-all-errors` on the Discord `curl` call was kept even
  after being shown NOT to be the actual fix for this incident: it's
  still genuine protection against a real future transient failure
  (actual rate limiting, a momentary Discord outage), just not what was
  wrong this time. Two independent protections for two independent
  failure modes, not one fix mistaken for the other.
- `ChangelogEntry.advanced.changes[].files?: string[]` replacing the
  entry-level `filesChanged: string[]`: chosen over keeping both (which
  risks the two silently drifting apart) — one field, per task, is the
  single source of truth, and the mapping work (all 21 entries,
  by hand) was accepted as a one-time cost specifically to avoid that
  future drift risk.
- `simple.summary: string | string[]` rather than always requiring an
  array: preserves every existing entry's simpler single-paragraph form
  untouched (no forced busywork rewriting 20 other entries) while giving
  a genuinely multi-point entry (today's v1.15.0) a real way to express
  that structure. A union type over a breaking type change.
- Supabase auth-option fix: `autoRefreshToken: false` chosen at the
  CLIENT-CONSTRUCTION level (both call sites) rather than, say, adding a
  process-wide client cache/singleton to avoid re-construction — the
  latter was considered implicitly but rejected as unnecessary: the real
  defect wasn't "constructing a client is expensive," it was "each
  client leaves a permanent uncleared timer," and disabling the
  unnecessary auto-refresh machinery entirely (which these two clients
  never legitimately need, since neither ever holds a real user session)
  fixes the actual defect with a two-line, zero-behavior-change diff
  rather than a larger architectural change (a shared client instance
  would also have been safe here, but wasn't needed once the root timer
  issue was addressed directly).
- Verification methodology: for the Discord embed-length fix, the exact
  jq truncation expression was tested against a synthetic 1200-character
  string BEFORE being committed. For the Supabase leak fix, the actual
  mechanism (setInterval calls) was directly intercepted and counted in
  an isolated script BEFORE claiming the fix worked, rather than relying
  on reading the library source alone. Both reflect a session-wide
  preference for empirical proof over plausible-sounding reasoning,
  especially after Step 8's rate-limiting misdiagnosis showed how easy
  it is to be confidently wrong without a direct test.
