[Step 4 — Keep-alive endpoint: implementation]
  * Event / Issue: implement it.
  * Resolution: new file app/api/ping/route.ts (Section 4 has the exact logic).
    Deviations from the literal request, each deliberate and disclosed to the user:
      a) Next.js route handler instead of Express.
      b) NO dummy table / NO migration: reads the existing, already
         anon-readable `site_settings` table
         (`.from("site_settings").select("id").limit(1)`), so the requested
         "CREATE TABLE ping_check" SQL was not needed.
      c) Cadence uses the UTC epoch-day count, NOT getDate() % 4:
         `Math.floor(now.getTime() / 86_400_000) % 4 === 0`. Reason: day-of-month
         multiples of 4 leave a gap of up to 7 days across month boundaries
         (28th -> 4th in a 31-day month = exactly 7 days), which is precisely
         Supabase's pause threshold. Epoch days give a strict 4-day cycle. The
         user was told how to revert (change the single `isDueDay` line).
      d) The DB query is fire-and-forget (`void (async () => {...})()`), so the
         HTTP response never waits on it and can never fail because of it.
      e) `lastDbPingDate` is set ONLY on success (spec said "update on run"),
         so a failed attempt is retried on the next ping that day; a
         module-level `dbPingInFlight` boolean prevents concurrent duplicate
         queries; failures are `console.error`'d, never thrown.
      f) Both GET and HEAD are exported (UptimeRobot's default check method is
         HEAD); `export const dynamic = "force-dynamic"`; response header
         `Cache-Control: no-store`.
      g) Uses createPublicClient() (auto-refresh ticker off) so this endpoint
         cannot reintroduce the 293fd7d leak.
    Log lines: `[keep-alive] Supabase ping OK (YYYY-MM-DD)` and
    `[keep-alive] Supabase ping FAILED: <message>`.
  * Associated Commit Hash: d6d6986 (Step 8).

[Step 19 — Way 1 implementation: components/embeds/FacebookEmbed.tsx]
  * Event / Issue: build Way 1 = replace "did an iframe appear" detection for
    videos with the SDK's xfbml.ready signal, and go straight to the outbound
    card (skipping the tier-2 direct iframe, which uses the same href and fails
    the same way) when the SDK loaded but no player became ready in 8000ms.
  * Resolution (exact logic):
      - `type XfbmlReadyMessage = { type?: string }`; `Window.FB` typing extended
        with `Event: { subscribe(event, cb), unsubscribe(event, cb) }`.
      - `type Failure = "sdk" | "unplayable"`. State `failure: Failure | null`
        replaces the old boolean `xfbmlFailed`; `iframeFailed` retained.
      - State `readyUrl: string | null` + derived `playerReady = readyUrl ===
        cleanUrl` (so a new link never inherits a previous link's "ready").
        `readyListenerRef` holds the subscribed callback.
      - `parseAndListen = useCallback(...)` (deps [cleanUrl, isVideo]): if

3. ARCHITECTURAL DECISIONS & "WHY" RATIONALE:
--------------------------------------------------------------------------------
- /api/ping is a Next.js route handler, not Express: the codebase is Next 16 App
  Router on Render `output: "standalone"`. It lives under app/api/ping so it
  inherits proxy.ts's CSP but bypasses the admin auth gate (scoped to /admin).
- No dummy table: an existing anon-readable table (site_settings) is a valid
  "wake the DB" read, avoids a migration on a production DB that has had
  migration-tracking drift ("remote":"" oddities, 2026-09-14/15), and avoids a
  new RLS surface.
- Epoch-day % 4 instead of getDate() % 4: getDate() % 4 gives a 7-day gap from
  the 28th to the 4th of 31-day months = Supabase's pause threshold. Epoch-day
  is an exact 4-day cycle. (Trade-off: due days are not "multiples of 4 of the
  month"; UTC boundaries, not IST.)
- Fire-and-forget DB call + success-only flag + in-flight guard: the health
  response must be instant and can never depend on the DB; retry-on-failure at
  most every ping interval; no concurrent duplicate queries.
- createPublicClient() for the ping: retains the autoRefreshToken:false /
  persistSession:false / detectSessionInUrl:false options that fixed the real
  Render OOM leak (293fd7d). Constructing a client only once per 4 days makes
  the residual cost negligible.
- Both GET and HEAD handlers: UptimeRobot commonly probes with HEAD; the Next
  docs list HEAD as an explicit method and do not promise auto-HEAD.
- Changelog: new v1.16.0 header (not a checkpoint append) because today's date
  differs from the top entry's date, per the standing convention.
- Facebook: hypotheses were treated as hypotheses. The music theory was tested
  and effectively refuted for the tested links; the working root cause candidate
  is unresolved share short-links. Real-browser evidence (Playwright + system
  Edge) was preferred over curl because Facebook bot-blocks curl/browser-UA
  server requests (proven 2026-09-15, re-observed today: browser-UA fetch -> 400).
- Way 1 design choices: (a) xfbml.ready as the success signal for VIDEOS only
  (validated empirically: fires for playable, absent for "Video Unavailable");
  (b) unavailable -> skip tier-2 iframe (same href, same failure); (c) keep the
  old chain when window.FB is undefined (SDK blocked) because the direct plugin
  iframe may still load; (d) post plugin path untouched (xfbml.ready was not
  measured for fb-post); (e) readyUrl-vs-cleanUrl comparison instead of a
  boolean to avoid stale "ready" across URL changes; (f) subscribe BEFORE parse
  so the ready event for that parse cannot be missed.
- KNOWN DESIGN RISK in Way 1 that may explain the user's "doesn't work":
  if xfbml.ready fails to fire in some environment even for playable videos
  (Safari/Firefox tracking protection, extensions, slow networks > 8s, ready
  fired before the listener attached), a playable video would be REPLACED by the
  "Facebook doesn't let this video play..." card — a regression. It also never
  makes a broken share/v link actually PLAY; it only degrades gracefully. If the
  user's expectation was "embeds must play", Way 1 by design cannot satisfy it.
- Newly discovered candidate ("Way R", NOT built): server-side share-link
  resolver. Resolve `/share/{v,r,p}/<code>` via `fetch(url, {redirect:"manual",
  headers:{"user-agent":"facebookexternalhit/1.1 (+http://www.facebook.com/
  externalhit_uatext.php)"}})`, read the `Location` header, strip `?rdid=`
  (and other tracking params), THEN re-run getEmbedInfo()/classification on the
  RESOLVED URL (important: share/v/14psGv8vWSy resolves to a /posts/pfbid URL,
  which must use fb-post, not fb-video), cache via unstable_cache with a long
  revalidate (server-side, cookie-free, consistent with the project's caching
  architecture), and on ANY failure fall back to the original URL (so Render's
  IP being blocked cannot cause a regression). Alternative delivery: one-time
  local script resolving all 182+ stored links and writing `resolved_url` into
  the posts.links JSONB (no schema migration; requires explicit user approval
  to write production data). Render-IP behavior is unknown until deployed and
  observed in Render logs.
- Alternatives evaluated and discarded today: see Step 11 "Ruled out" list.
