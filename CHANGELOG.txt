[v1.16.0] - 2026-09-19

* Added: New keep-alive endpoint, GET/HEAD /api/ping
  (app/api/ping/route.ts), meant to be polled by an external uptime
  monitor (UptimeRobot) pointed at the Render .onrender.com URL. Every
  request returns an immediate 200 with { status: "ok", uptime }
  (Cache-Control: no-store), which keeps the Render instance awake.
  Separately, on every 4th UTC epoch-day it fires one background,
  fire-and-forget "select id from site_settings limit 1" through
  createPublicClient() so Supabase's 7-day inactivity auto-pause never
  triggers; a module-level lastDbPingDate flag ensures that query runs
  at most once per due day, it is only set on success (a failure is
  retried on the next ping and logged, never surfaced to the caller),
  and the response never waits on it. Epoch-day cadence was chosen over
  getDate() % 4 because day-of-month multiples of 4 leave a 7-day gap
  across month boundaries (28th to 4th in a 31-day month), exactly
  Supabase's pause threshold. No new table or migration: site_settings
  is already anon-readable via RLS.

Files edited (paths only):
  - app/api/ping/route.ts (new)

[v1.14.0] - 2026-09-16

* Fixed: Render production was crashing repeatedly with exit status 134
  (V8 "JavaScript heap out of memory", confirmed from the actual crash
  log tail - not a native-module or assertion failure). Root cause: the
  container's auto-sized V8 heap ceiling (~256MB) left almost no
  headroom over the app's own steady-state footprint, and
  app/api/admin/upload/route.ts fully buffered uploads in memory with a
  100MB video cap - a single admin video upload could transiently
  double-buffer ~200MB on top of that baseline. MAX_VIDEO_BYTES reduced
  100MB to 25MB; experimental.serverActions.bodySizeLimit reduced 30mb
  to 1mb (a leftover from the pre-R2-migration complaint upload path,
  now dead code - see v1.13.0). Raising the actual heap ceiling requires
  a Render dashboard environment variable
  (NODE_OPTIONS=--max-old-space-size=400, documented in .env.example)
  that only the account owner can add.
* Added: instrumentation.ts/instrumentation-node.ts - periodic
  process.memoryUsage() logging (15 min interval) and onRequestError
  logging with error digests, so a future crash leaves a trace instead
  of a bare native stack.
* Added: Admin dashboard instant navigation feedback via a shared
  useTransition-backed pending state (AdminNavPendingContext) - every
  sidebar nav link and Settings sub-tab link now shows a top progress
  bar and disables itself the instant it's clicked, so rage-clicking
  can't stack up multiple concurrent server requests.
* Added: app/admin/(protected)/loading.tsx - a shared skeleton fallback
  so a slow page's own data fetch streams in behind a visible loading
  state instead of a blank pane (does not cover the shared layout's own
  auth fetch - see Changed, below).
* Changed: /admin/settings now fetches only the active tab's data
  instead of unconditionally querying all 9 tables behind every one of
  the 6 tabs on every page load.
* Changed: The admin layout, Overview page, and Settings page now share
  one react cache()-wrapped auth/profile lookup (lib/admin-auth.ts)
  instead of each independently calling Supabase Auth - cuts up to 3
  sequential round trips per navigation down to 1.
* Changed: posts/features/phases admin list queries capped at
  .limit(200) - unpaginated by design, but no longer truly unbounded on
  a memory-constrained host.
* Changed: The 6 heaviest @dnd-kit-based Settings managers
  (Organizations, CTA Buttons, Footer Blocks, Social Links, Header
  Navigation, Users) now load via next/dynamic, so /admin/settings's
  client bundle only pays for whichever tab is actually open.
* Changed: Session inactivity timer (SessionTimer.tsx) no longer resets
  on scroll/touchstart - only a deliberate pointerdown or keydown keeps
  the 15-minute session alive, so a page left merely scrolled still
  signs out on schedule.
* Security: Dedicated security review of this entry's diff (dashboard
  latency + OOM fixes): no high- or medium-confidence findings. The
  react cache() auth/profile dedup pattern is the standard,
  request-scoped App Router idiom (no cross-user leakage risk); all
  body-size/upload-cap changes narrow rather than widen accepted input;
  the per-tab Settings fetch doesn't change what's ever serialized to
  the client, since React Server Components already only ship rendered
  output, not unrendered sibling props.
* Security: Repository-wide dead-code/dependency audit: eslint . clean
  (0 findings), no unused top-level or nested components/ files, no
  unused package.json dependencies, no orphaned public/ assets, no
  commented-out code blocks found. No removals were necessary.

[v1.13.0] - 2026-09-15

* Added: Cloudflare R2 as primary object storage for admin media
  (site/post/feature/phase images), via a server-side upload proxy
  (app/api/admin/upload/route.ts) - a browser can never hold R2's
  signing key directly, so every admin media component now uploads
  through this route instead of straight to Supabase Storage.
* Added: One-off migration script
  (scripts/migrate-supabase-to-r2.ts, npm run migrate:r2) that copies
  every existing Supabase Storage file to R2 and rewrites every stored
  URL across posts/settings/features/organizations/phases. Ran
  successfully: 402 files transferred, 0 failed, 390 DB rows updated.
  Nothing was deleted from Supabase Storage.
* Added: Citizen complaint attachments also move to R2, but through a
  separate, private bucket (R2_COMPLAINT_BUCKET_NAME) reached only via
  presigned PUT (upload)/GET (admin view) URLs - the admin-media
  bucket has public access enabled, and Cloudflare's public-access
  toggle is bucket-wide, so mixing private submissions into it would
  have exposed them.
* Added: Client-side WebP image compression (browser-image-
  compression) and WebCodecs-based video re-encoding for complaint
  uploads (fast-track under 10MB as-is, otherwise re-encoded in-
  browser to 720p/30fps/1.2Mbps via mp4-muxer, with a "trim your
  video" prompt as the final fallback) - no file bytes pass through
  the Next.js server for complaint media.
* Added: Usage Metrics dashboard (/admin/usage, Simple/Advanced dual
  mode) replacing the Egress Monitor - real R2 storage size/object
  counts (lib/r2-usage.ts) alongside the existing Supabase egress
  telemetry, with live R2 Class A/B operation counts as an optional
  add-on behind CLOUDFLARE_API_TOKEN that degrades gracefully to "not
  connected" without it.
* Changed: Storage deletes (both admin media and complaint media)
  route to R2 or legacy Supabase Storage per-object based on key shape
  (lib/storage-delete.ts, lib/complaint-storage-delete.ts), since both
  backends coexist until the old Supabase buckets are cleaned up by
  hand.
* Changed: /admin/egress now redirects to /admin/usage.
* Fixed: The migration script's header-corruption bug -
  .env.local's CRLF line endings were leaking a stray \r into R2's
  signed Authorization header, causing every request to fail with
  "Invalid character in header content". Fixed by sanitizing every
  value read from .env.local (strip quotes, \r, \n) before use.
* Security: Complaint attachments deliberately kept out of the public
  R2 bucket (see Added, above) to avoid exposing private citizen
  submissions through a bucket-wide public-access toggle.

Correctness note:
  The task's literal "export const revalidate = 60" snippet was a
  no-op here - this site's proxy.ts issues a fresh per-request CSP
  nonce on every route, which Next.js's own docs say requires dynamic
  rendering site-wide (confirmed by building with that export set and
  seeing the route stay dynamic, not become ISR'd). Caching therefore
  happens one level down, at the data-fetch layer, not the route
  layer. One page (app/(site)/page.tsx) briefly became static/ISR by
  accident once its data-fetch stopped needing a Dynamic API
  (cookies) - caught by curling a built+started production server
  twice and finding the cached HTML's embedded script nonce no longer
  matched the live CSP header (would have blocked all scripts in a
  real browser). Fixed with an explicit, documented
  "export const dynamic = 'force-dynamic'" on that page. The admin
  dashboard was already effectively uncached by construction (its
  Supabase client always reads cookies first) and remains untouched.

  * Replaced the hand-authored static HTML/CSS site with the current
    dynamic Next.js application: the public site (homepage, post
    pages, complaint form), the full admin dashboard (auth, Features,
    Posts, Complaints), and the initial Supabase schema/RLS/storage
    setup. ~106 files added in one commit (0f06030) - this is the
    actual starting point of the application this changelog
    documents; see that commit directly for the complete file list.
  * Added a citizen complaint retention policy: purgeExpiredComplaints()
    (lib/complaints-cleanup.ts) permanently deletes any complaint past
    its expires_at timestamp - row, media rows, and the underlying
    storage files, with no "expired" state left to view. Runs both
    inline on every admin dashboard load and via an unauthenticated
    cron endpoint (app/api/cron/purge-complaints/route.ts, optionally
    gated behind CRON_SECRET) for true background deletion independent
    of an admin ever opening the dashboard.
  * Added .env.example, .gitignore, and this project's
    AGENTS.md/CLAUDE.md convention (read node_modules/next/dist/docs/
    before writing code, since this is a pinned Next.js version with
    training-data-diverging APIs).

Files edited (paths only):
  - Full application scaffold - see commit 0f06030 for the complete
    ~106-file list. Notable additions: app/(site)/*, app/admin/*,
    utils/supabase/{admin,client,middleware,server}.ts,
    supabase/migrations/20260911170000_complaints.sql,
    supabase/migrations/20260911220000_complaint_status.sql.
